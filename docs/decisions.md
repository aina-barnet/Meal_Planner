# Decision log

Decisions not fixed by the original brief, with the reason for each.

## Agreed with the owner

- **Language: Catalan** for the UI and the whole recipe catalogue (names, descriptions, steps, ingredient names). Code, identifiers and API field names stay in English.
- **Diners are members, not anonymous counts.** Each meal records which members eat it and where (`HOME` or `TAKEAWAY`) in `meal_attendee`. `dinersAtHome` and `dinersTakeaway` are derived counts. This lets the generator apply exactly the allergies and diets of the people eating that meal.
- **Lunch and dinner only.** Breakfast and snacks are personal and outside the plan.
- **Git: GitHub repository** (`aina-barnet/Meal_Planner`), commits on `main`. GitHub Actions (`.github/workflows/ci.yml`) runs `./gradlew test` and the web lint and build on every push and pull request to `main`.

## Milestone 1 — skeleton, schema, seed

- **Versions:** Spring Boot 4.1.1, Gradle 9.7.1 wrapper (generated by start.spring.io), springdoc-openapi 3.1.1, PostgreSQL 17, Node 24, Vite 8, React 19, Tailwind 4.
- **Gradle lives in `/api`** (`cd api && ./gradlew test`), so the API is a self-contained Docker build context.
- **Ports:** web on 3000 (nginx serving the bundle and proxying `/api`), API on 8080, database on 5432. Credentials are fixed in `docker-compose.yml` (local-only app, no `.env` to fill in).
- **Enums as `VARCHAR` + `CHECK`** rather than PostgreSQL enum types: readable, easy to evolve with Flyway, and the Java enums stay the single source of truth.
- **Allergens** use the 14 EU-declared allergens (Reg. 1169/2011). Ingredients carry allergen tags; members declare allergies or intolerances against the same list (both are hard constraints).
- **Diet types:** omnivore, pescatarian, vegetarian, vegan. Diet compatibility is derived from ingredient categories (meat, fish, seafood, dairy, egg), not from a hand-set recipe flag, so it cannot drift from the ingredient list. Chicken broth is categorised as meat and fish stock as fish for this reason.
- **Unit conversion:** metric conversions (kg→g, l→ml, cl→ml) are generic; everything else (unit, tbsp, tsp, clove, pinch, slice, bunch, sprig, can) is ingredient-specific in `ingredient_unit_conversion`. A seed test asserts that every recipe line converts.
- **Lunchbox suitability was set conservatively:** paella-style rice, grilled or baked fish fillets, shellfish, fried eggs and grilled meat are not portable. Stews, legumes, oven dishes, pasta, cold salads and Spanish omelettes are. Result: 36 of 50 recipes are portable, 7 of them vegan.
- **Week plans start on Monday** (enforced by a `CHECK`).
- **Single household** enforced by a unique index on a constant expression.

## Milestone 2 — domain

- **Packages:** `domain.catalogue` (ingredients, recipes, units), `domain.planning` (servings). `DomainPurityTest` fails the build if any domain file imports Spring, Jakarta/JPA, Hibernate or the application layers.
- **Quantities are `BigDecimal`**.
- **Extra servings** are cooked.

## Milestone 3 — API and persistence

- **Layers:** `persistence` (JPA entities + Spring Data repositories), `application` (transactional services that map entities to domain objects and call the domain), `web` (controllers, DTOs, error handling). Entities never leave the application layer as API bodies.
- **The catalogue is loaded once into memory** as domain objects. It only changes through migrations, so every planning operation is an in-memory domain computation.
- **Manual assignment enforces all hard constraints**, not only the lunchbox rule: allergies/intolerances and diet type are checked too, by the same `MealAssignmentRules` the generator will use.
- **A new week is pre-planned:** 7 lunches and 7 dinners with every member at home, ready to adjust in the week configuration screen.
- **Reconfiguring diners keeps dishes** on meals that keep their day and slot. If the new diners make a dish invalid (someone now takes a lunchbox), the dish is removed and `emptyReason` says why, instead of rejecting the whole configuration.
- **Swapping moves locks with the dish**, and both directions must satisfy the constraints.
- **Confirmation requires every meal to have a dish**. Confirmed weeks are read-only (409 `WEEK_CONFIRMED`).
- **Errors** are RFC 9457 problem details with a machine-readable `code`; 422 business rule violations also carry human-readable `reasons` in Catalan, which the UI shows as is.
- **Integration tests can target an external database** via `TEST_DB_URL` (they wipe it); otherwise Testcontainers starts PostgreSQL. CI uses Testcontainers.

## Milestone 4 — setup wizard and week configuration

- **No routing library:** four screens use a ~60-line hash router (`#/llar`, `#/setmana/:id`, `#/menu/:id`), keeping the stack to what the brief fixes.
- **Wizard in two steps:** household name, members (list + form). The household step can be revisited; once a household exists the wizard opens on the members step.
- **Allergen chips cycle** none → allergy → intolerance.
- **Week configuration is a 7 × 2 grid.** Each member has a three-way toggle per meal (home / lunchbox / not eating) plus an extra-servings stepper. "Quick patterns" set a member's weekday lunches in one click, the most common real-life case (lunchbox Monday to Friday). Changes are edited locally and saved in one request.
- **Palette (superseded, see below):** olive and terracotta on warm stone.

## Milestone 5 — menu board and manual assignment

- **The menu board already uses dnd-kit** (drag a dish onto another meal to swap), so milestone 6 only plugs the generator in. Drops are checked on the client against the same hard constraints as the API (`rules.ts` mirrors `MealAssignmentRules`): invalid targets turn terracotta while dragging and show the reason on hover; a blocked drop explains why in a toast. The API re-checks and rolls back the optimistic swap on error.
- **The recipe picker** lists only recipes allowed for that meal (`/allowed-recipes`), with search and protein filters.

## Milestone 6 — generator

- **`MenuGenerator` is a pure domain class** taking the catalogue, the meals to fill (diners, locked dish), previous weeks' history and an injected `RandomGenerator`. The scoring and its weights are documented in the class comment.
- **No repeats within a week** while alternatives exist: dishes already on the menu are set aside before scoring. Tests showed that a pure score penalty still let an occasional repeat through the random draw.
- **Randomness:** one of the top five is drawn with probability proportional to score³, so regenerating gives a different but still well-fitting week.
- **Locked meals** keep their dish and count as decided from the start, so the rest of the week varies around them.
- **Empty meals** carry a Catalan explanation of which constraints ruled the catalogue out (e.g. "14 no aguanten la carmanyola; 9 contenen gluten (Marta)").
- **History** looks back 28 days over the household's other weeks.

## After milestone 6

- **Adjustable text size** (A−/A+ in the header, 100–150 %, remembered per browser). All sizes are in rem, so the whole interface scales.
- **Back to draft:** a confirmed week can be reopened (`POST /api/weeks/{id}/reopen`) when it was confirmed by mistake.
- **Local persistence without Docker:** until Docker runs on the owner's machine, PostgreSQL runs from `%LOCALAPPDATA%\meal-planner` (portable binaries + data directory) with start/stop scripts there. This is outside the repository on purpose; with Docker, the `pgdata` named volume plays that role.
- **Own recipes and ingredients (agreed with the owner):** every recipe can be edited, seeded ones included, and recipes are hidden instead of deleted (`recipe.hidden`) so past weeks keep resolving them; hidden recipes are left out of the generator and the picker. The family can add ingredients with allergens and unit equivalences; only their own ingredients are editable, and an edit that would leave a recipe line unconvertible is rejected (422 `INGREDIENT_IN_USE`). Recipe lines are validated against the ingredient's supported units. Editing a recipe affects new menus.
- **Printing in two formats:** an "Imprimeix" menu (menu board) prints the weekly menu (A4 landscape grid: dish, protein, time, diners at home and lunchboxes). The chosen sheet is rendered outside the app root, measured off-screen and scaled down with CSS zoom if needed, so it always fits on one page. Print sizes are in points/mm, independent of the on-screen text size.
- **Protein types are data** (V5, table `protein`): the 11 seeded types keep their codes and get Catalan names; the family can add their own (generated code `custom-…`), rename them, and delete them while no recipe uses them. In the domain `ProteinType` became a value record (the seeded ones remain as constants), so the generator's rotation works the same for custom types. Recipes reference `protein(code)` with a foreign key.
- **Copying a menu** (`POST /api/weeks/{id}/copy`): same dish, diners and extra servings per day and slot onto another week. The target week is created if needed; a draft target has its meals replaced (the UI asks first); a confirmed target is refused. Members removed since are dropped from the copy, and dishes that no longer fit the diners are removed with the reason, as when reconfiguring a week.
- **Visual identity after the owner's reference poster ("Asesoría nutricional"):** butter-cream background, vivid orange (#ff5a0a) for primary actions, active tabs and page titles, avocado green for what is good (at home, confirmed, own items), coral (the avocado stone) for lunchboxes and warnings. Titles use Lilita One, upper-case for page titles; the font is bundled with `@fontsource/lilita-one` so the app still works offline. Logo: half an avocado with an orange spark. Print sheets keep their plain black-on-white style.

## Focus on organising the week, not on nutrition

- **Calories and macronutrients removed (agreed with the owner).** The app is for organising the household's week: what is eaten at each meal, who takes a lunchbox and what to buy. Members no longer have birth date, sex, weight, height, activity level, kcal override or main meals share; ingredients no longer carry nutrition per 100 g; recipes and meals no longer show kcal or a kcal fit. V6 drops those columns. Portions were already one serving per diner, so quantities and the shopping list are unchanged. The generator's kcal-fit criterion is gone and the remaining weights were rescaled: protein rotation 40 %, variety 30 %, recency 30 %. The setup wizard has two steps. Earlier entries in this log that mention kcal describe the app as it was then.
- **No shopping and no pantry (agreed with the owner).** The app organises the meals, not the shopping. The pantry, the shopping list (and its print sheet), the purchase data of ingredients (package size, aisle, pantry staple) and the scaling mode of recipe lines are gone; V7 drops their tables and columns. Ingredients, quantities and steps stay in the recipes: allergens and diets are still derived from the ingredients. Members' dislikes are gone too, with the generator's dislike penalty and the meal notes. Confirming a week now only marks the menu as final (every meal needs a dish) and going back to draft just reopens it.
- **Simpler dishes and members (agreed with the owner).** A dish is name, servings, time, main protein, "lunchbox-friendly? yes/no" (every dish can be eaten at home), ingredients and steps. Description, cuisine, seasons and the cold-or-reheat distinction are gone (V8); with cuisine gone, the generator's variety criterion is only about vegetables not yet used this week. Members are name, diet and allergies; the free-text diet notes are gone. The printed menu names who eats at home, who takes a lunchbox and who is away (members not at that meal; "Fora: tothom" for meals not planned), and each dish on the menu board has a print icon for its recipe sheet (also on confirmed weeks).
- **Monday to Friday only (agreed with the owner).** Weekends are not planned: new weeks have 10 meals, a configuration with a Saturday or Sunday meal is rejected, copying a week leaves weekend meals out, and V9 deletes the weekend meals of existing weeks. Weeks still start on Monday.
